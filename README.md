# Задание 1. Резервное копирование

Кейс
Финансовая компания решила увеличить надёжность работы баз данных и их резервного копирования.

Необходимо описать, какие варианты резервного копирования подходят в случаях:

## 1.1. Необходимо восстанавливать данные в полном объёме за предыдущий день.

Для этого случая идеально подходит полное резервное копирование (Full Backup), выполняемое по расписанию один раз в сутки (например, ночью, когда нагрузка на финансовую систему минимальна).

**Как это работает** : Каждую ночь специальный скрипт делает полный снимок всей базы данных (дамп) и сохраняет его на отдельный сервер бэкапов.

**Процесс восстановления** : Если база ломается сегодня, мы просто берем ночной файл бэкапа за вчерашний день и полностью разворачиваем его. Данные будут восстановлены ровно на тот момент, когда бэкап завершился.

**Альтернатива** : Если база огромная, можно делать Полный бэкап раз в неделю (например, в воскресенье), а каждую ночь делать дифференциальный бэкап (Differential Backup), который сохраняет только изменения, произошедшие с момента последнего полного бэкапа.

**Решает задачу хранения истории (Full Backup)**

## 1.2. Необходимо восстанавливать данные за час до предполагаемой поломки.

Для выполнения этого требования одного лишь ежедневного бэкапа недостаточно. Финансовой компании необходимо использовать резервное копирование журналов транзакций / инкрементальный бэкап (Incremental / Transaction Log Backup).

**Как это работает** : В СУБД (например, PostgreSQL или MySQL) включается режим записи всех изменений в специальные файлы-журналы (WAL — Write-Ahead Logs или Binlog). Эти журналы копируются на сервер бэкапов с высокой частотой — например, каждые 15–30 минут.

**Процесс восстановления** : При аварии мы сначала восстанавливаем последний ночной Полный бэкап (из пункта 1.1), а затем «накатываем» поверх него цепочку журналов транзакций вплоть до нужного часа (этот метод называется Point-in-Time Recovery или PITR). Мы сможем восстановить базу с точностью до минуты или даже секунды перед сбоем, минимизировав потери.

**Решает задачу минимизации потери данных (RPO — Recovery Point Objective) с помощью логов транзакций (PITR)**.

# Задание 2. PostgreSQL

## 2.1. С помощью официальной документации приведите пример команды резервирования данных и восстановления БД (pgdump/pgrestore).

### 1. Команда резервирования (pg_dump)

Эта команда создаёт резервную копию одной конкретной базы данных в специальном сжатом бинарном формате.

*pg_dump -h localhost -p 5432 -U postgres -F c -b -v -f /path/to/backup/my_db_backup.dump my_database*

Ключи команды:
**-h localhost** — адрес сервера, где запущена база данных (в данном случае локальный ПК).
**-p 5432** — сетевой порт PostgreSQL (по умолчанию 5432).
**-U postgres** — имя пользователя (суперпользователя), от чьего имени делается бэкап.
**-F c ** — (Важно!) выбор формата архива. c означает custom (кастомный архив). Он сжимает данные и позволяет восстанавливать базу выборочно.
**-b** — включать в бэкап большие объекты (blobs).
**-v** — режим детального вывода (verbose). Консоль будет показывать, какие таблицы сейчас копируются.
**-f** /path/to/backup/my_db_backup.dump — путь и имя файла, куда сохранится бэкап.
**my_database** — имя базы данных, которую мы хотим скопировать.

### 2. Команда восстановления (pg_restore)

Эта команда используется для разворачивания бэкапа, созданного в кастомном формате (-F c), в новую или чистую базу данных.

*pg_restore -h localhost -p 5432 -U postgres -d my_database_restored -v /path/to/backup/my_db_backup.dump*

Ключи команды:
**-h, -p, -U** — те же самые параметры подключения к серверу.
**-d my_database_restored** — имя базы данных, в которую будут восстанавливаться данные (целевая база должна быть заранее создана пустой).
**-v** — детальный вывод процесса восстановления в консоль.
**/path/to/backup/my_db_backup.dump** — путь к файлу бэкапа, который мы создали на предыдущем шаге.

## Резервирование в SQL-текст:

*pg_dump -U postgres my_database > my_backup.sql*

## Восстановление из SQL-текста (здесь pg_restore не сработает, используется обычная утилита psql):

bash

*psql -U postgres my_database_restored < my_backup.sql*

# Задание 3. MySQL

Полноценный инкрементный бэкап в MySQL реализуется с помощью встроенной утилиты mysqldump и механизма бинарных логов (Binary Logs), в которые СУБД непрерывно записывает все новые изменения данных.

## 1. Создание базового полного бэкапа и запуск отсчёта инкрементов:

*mysqldump --all-databases --single-transaction --flush-logs --master-data=2 -u root -p > /var/backups/full_base.sql*

Ключ **--flush-logs** закрывает текущий файл бинарного лога и открывает новый чистый файл. Именно с этого момента начинается отсчёт изменений.

## 2. Команда создания инкрементного бэкапа (в конце часа/дня): Чтобы зафиксировать накопившиеся изменения (инкремент), выполняется команда сброса и ротации логов:

*mysqladmin -u root -p flush-logs*

После этого текущий файл бинарного лога (например, mysql-bin.000001), содержащий все изменения за прошедший период, закрывается и копируется в архив. Он и является инкрементным бэкапом. СУБД при этом автоматически переходит на запись в следующий файл (mysql-bin.000002).
